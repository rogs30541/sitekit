# SiteKit 雙平台部署架構（Zeabur ／ Cloudflare＋D1＋Resend）

> 目標：同一套 SiteKit 能以兩種方式交付——
> **A. Zeabur（容器）**：Next.js＋NestJS＋PostgreSQL（現行，v0.16.5 上線中）
> **B. Cloudflare（無伺服器）**：Workers＋D1＋R2＋Resend＋Queues
> 原則：**業務邏輯只寫一次**，兩平台各自只有「薄殼」（HTTP 框架、DB 驅動、儲存、信件、排程、佇列）。

---

## 1. 現況與差距

| 項目 | 現況（apps/api＋apps/web） | Cloudflare 能否直接用 |
|---|---|---|
| Web | Next.js 15 App Router，`output: standalone`，`/api/*` 以 rewrites 反向代理到 api | 可，走 **OpenNext（@opennextjs/cloudflare）** 跑在 Workers；rewrites 改成 **Service Binding** 呼叫 api Worker |
| API 框架 | NestJS 11（Express、DI、Guard、helmet、cookie-parser） | **不可**：Workers 沒有 Node HTTP server；HTTP 殼要換 **Hono**（apps/edge 已有 348 行草稿） |
| 資料庫 | Prisma 6 ＋ PostgreSQL：34 model、6 enum、15 個 Json 欄、3 個 `String[]`、19 個 migration | **D1＝SQLite**：無 enum／陣列／原生 Json；Prisma 有 `@prisma/adapter-d1`，但 schema 要另一份 sqlite 版；migration SQL 要重產 |
| 物件儲存 | `StorageService`：local 或 S3 相容（SigV4，免 SDK） | 可：R2 走 S3 相容端點（同一段程式），或改 R2 binding（零金鑰） |
| Email | `NotifyService`：log 或 Resend（HTTP） | 可：Resend 本來就是 HTTP，直接共用 |
| LINE 推播、金流、物流、發票、AI | 全部是 HTTPS fetch＋簽章（Node `crypto`） | 可：Workers 有 `nodejs_compat`（crypto／Buffer）；已用 `fetch` 無 axios |
| AI 產圖佇列 | `StudioService` 程序內序列佇列＋重啟補跑 | Workers 單請求 CPU 上限，產圖 30–120 秒 → 要改 **Queues consumer**（15 分鐘） |
| 排程 | `expire_orders` 等由後台手動或外部呼叫 | **Cron Triggers** |
| 限流 | 程序內記憶體 | **Rate Limiting binding** 或 KV |
| Session | DB 表（`sessions`／`admin_sessions`，cookie 只存 id） | 相同（D1 表） |
| Redis | 宣告未使用 | 不需要 |
| 設定快取 | `SettingsService` 30 秒程序內快取 | Workers isolate 不保證常駐 → 改 **KV**（或每請求直讀 D1，設定表很小） |

**結論**：Web 幾乎零改；API 的「HTTP 殼＋DB 驅動＋佇列」要換，**業務邏輯要先從 NestJS 抽出來**才能共用。

## 2. 目標架構：一核心、兩薄殼

```
packages/
  shared/          既有：型別、SETTING_KEYS、OPS_ACTIONS、design/sales/tracking（純 TS，兩邊共用）
  core/            ★新增：所有業務服務（純 TS class，不依賴 Nest／Hono／Node）
    ports/         介面：Db、Storage、Mailer、Queue、Clock、RateLimiter、Env
    services/      orders、payments(gateways)、catalog、content、sales、learn、
                   studio、members、settings、notify、invoice、logistics、ops(run)…
    http-errors.ts 自家 HttpError(status, message)（取代 @nestjs/common 的 Exception）
  db/              ★新增：Prisma schema 單一來源 + 產生器
    schema.model   一份模型（含註解標記）
    postgres/schema.prisma   由產生器輸出（enum／Json／String[] 原樣）
    sqlite/schema.prisma     由產生器輸出（enum→String、Json→String(JSON)、String[]→String(JSON)）
    migrations/postgres/     prisma migrate（現有 19 個搬過來）
    migrations/d1/           wrangler d1 migrations（由 prisma migrate diff 產 SQL）

apps/
  web/             Next.js（共用）；平台差異只在 next.config：rewrites(Zeabur) vs service binding(CF)
  api/             Zeabur 薄殼：NestJS controllers → 只做 DTO 驗證、呼叫 core services；PrismaService(pg)
  worker/          Cloudflare 薄殼：Hono routes → 同一份 core services；Prisma D1 adapter；R2/Queue/Cron/KV bindings
  edge/            現有草稿 → 併入 apps/worker 後刪除
mcp/               共用（打 api 的 /api/ops，與平台無關）
```

### 2.1 core 的 ports（兩平台各自實作）

| Port | Zeabur 實作 | Cloudflare 實作 |
|---|---|---|
| `Db` | `PrismaClient`（postgresql） | `new PrismaClient({ adapter: new PrismaD1(env.DB) })` |
| `Storage` | local 磁碟 或 S3(R2) SigV4 | R2 binding（`env.BUCKET.put`）；公開網址走自訂網域或 `/api/assets` 轉發 |
| `Mailer` | Resend HTTP／log | Resend HTTP（同一段） |
| `Queue` | 程序內序列（現行）；可換 BullMQ | Cloudflare Queues（producer 在 request、consumer 另一個 handler） |
| `Scheduler` | 外部 cron 或 Nest `@Cron` | Cron Triggers（`scheduled()` handler） |
| `RateLimiter` | 記憶體 Map | Rate Limiting binding |
| `Cache`（settings） | 記憶體 30 秒 | KV（TTL 30 秒），`update_settings` 後 delete |
| `Env` | `process.env` | `env` bindings（secrets 用 `wrangler secret`） |

**Json 欄位處理**：core 只碰「已 parse 的物件」；`Db` port 的 sqlite 實作在讀寫時自動 `JSON.parse/stringify`（Prisma 中介層 `$extends` query hook 或在 repository 統一做）。`String[]`（`allowedFeatures`、`tags` 等 3 處）同樣以 JSON 字串存。Enum 改為 `String` 欄＋zod 驗證（core 裡本來就有 zod）。

### 2.2 兩平台的請求路徑

```
Zeabur
  瀏覽器 → web(Next, 8080) ──rewrites /api/*──> api(Nest, 8080) → Postgres
                                                  └→ 伺服器硬碟/R2、Resend、程序內佇列

Cloudflare
  瀏覽器 → web Worker(OpenNext) ──Service Binding env.API.fetch()──> api Worker(Hono)
                                                                       ├→ D1（Prisma D1 adapter）
                                                                       ├→ R2 binding（上傳／產圖結果／模板封面）
                                                                       ├→ KV（settings 快取、301 導向表）
                                                                       ├→ Queues（AI 產圖、批量匯入、寄信重試）
                                                                       ├→ Cron（逾期訂單、每日備份到 R2、ISR 重驗）
                                                                       └→ Resend／金流／物流／發票／AI（HTTPS）
  MCP（本機 stdio）→ Bearer OPS_TOKEN → 任一平台的 /api/ops/run
```

## 3. D1 的硬限制與對策

| 限制 | 影響 | 對策 |
|---|---|---|
| 單一資料庫 10 GB、單一寫入者 | 中小型站足夠；高併發下單會排隊 | 訂單／庫存交易本來就是短交易；超過規模改 Hyperdrive＋Postgres（core 不用改，換 Db 實作） |
| 無 enum／陣列／原生 Json | schema 要有 sqlite 版 | `packages/db` 產生器自動轉換，禁止手改兩份 |
| 交易：D1 只有 `batch()`，無互動式 transaction | `OrdersService.markPaid` 目前用 `prisma.$transaction(async tx => …)` 互動式 | 改寫成「先讀後算、最後一批 `batch` 寫入」；庫存扣減用 `UPDATE … WHERE stock >= qty` 條件式更新確保不超賣 |
| 每請求 CPU 時間（免費 10 ms／付費 30 s）、子請求數上限 | 產圖、批量匯入、報表 CSV 匯出可能超時 | 產圖、匯入走 Queues；CSV 匯出串流分頁 |
| 沒有檔案系統 | `storage.driver=local` 不存在 | Cloudflare 只允許 R2；安裝精靈強制 |
| Prisma 引擎大小 | Worker 壓縮後 1 MB（免費）／10 MB（付費）上限 | Prisma 6 在 Workers 需 `engineType = "client"`（無 Rust 引擎）＋ driver adapter；實測體積後決定；備案：core 的 `Db` port 改 Drizzle（pg＋sqlite 兩套 schema 可由同一份 model 產生） |
| 建置時的 `API_INTERNAL_URL` | Next rewrites 在建置時定案 | Cloudflare 走 Service Binding，不需要 URL；Zeabur 維持 build arg |

## 4. Web（Next.js）在兩平台

| 項目 | Zeabur | Cloudflare |
|---|---|---|
| 建置 | `next build`（standalone）→ Dockerfile.web | `opennextjs-cloudflare build` → `wrangler deploy` |
| `/api/*` | `rewrites` → `API_INTERNAL_URL` | `middleware.ts`／route handler 用 `env.API.fetch(req)`（Service Binding）；或 Cloudflare Route 把 `/api/*` 直接指到 api Worker（更簡單，web 不經手） |
| ISR／快取 | Next 內建（磁碟） | OpenNext incremental cache → R2（或 KV），tag cache → D1 |
| 圖片 | `<img>` 原生（未用 next/image） | 相同；可加 Cloudflare Images 但非必要 |
| 環境變數 | `NEXT_PUBLIC_*` 建置時 | 相同（wrangler `[vars]`）；`site.url` 一律從 settings 表讀，避免烘進映像 |

**建議把 `/api/*` 路由在 Cloudflare 直接綁到 api Worker**（同網域、cookie 同源），web Worker 完全不知道 api 存在，與 Zeabur 的「反向代理」等價。

## 5. 一次建置、兩種產出（CI）

```
tag v*  ─┬─ build shared + core + db(產兩份 schema)
         ├─ Zeabur：docker build Dockerfile.api / Dockerfile.web → ghcr.io/<org>/sitekit-{api,web}:<版號>
         └─ Cloudflare：wrangler deploy apps/worker（含 D1 migrations apply --remote）
                        opennextjs-cloudflare deploy apps/web
```

- 測試矩陣：同一套 e2e（`tests/e2e/*.mjs`，只打 HTTP）分別對 `localhost:4000`（Nest＋pg）與 `wrangler dev`（Hono＋D1 local）跑，**兩平台行為一致**由這套測試保證。
- 版本號三個 package.json 改由 release 腳本統一升。

## 6. 遷移路線（建議順序）

| 階段 | 內容 | 可交付物 | 估計 |
|---|---|---|---|
| **M0 現況固化（✅ v0.17.x 完成）** | e2e 進 repo＋CI 起 postgres 跑；移除 apps/edge 殘留；R2＋Resend 在 Zeabur 先啟用（兩平台共通的儲存／信件先統一） | Zeabur 版行為不變、測試護欄就位 | 1–2 天 |
| **M1 抽 core（✅ v0.18.0 完成）** | 把 `apps/api/src/modules/*/**.service.ts` 搬到 `packages/core`，去掉 Nest 依賴（Exception→HttpError、`@Injectable` 移除、建構子改傳 ports）；Nest controllers 改為薄殼 | Zeabur 版通過同一套 e2e | 3–4 天 |
| **M2 db 雙 schema（✅ v0.20.0：postgres＋sqlite；mysql 待需求）** | `packages/db` 產生器：postgres／sqlite 兩份 Prisma schema＋migration；Json／陣列／enum 轉換層；`markPaid` 等互動式交易改 batch 版 | 本機用 sqlite 檔跑通全部 e2e | 2–3 天 |
| **M3 Cloudflare 殼** | `apps/worker`（Hono）：路由對照 Nest controllers 逐條映射；R2／KV／Queues／Cron 實作 ports；OpenNext 建置 web；`wrangler dev` 跑 e2e | Cloudflare 預覽環境上線 | 3–5 天 |
| **M4 交付化** | 安裝精靈（首位管理員、網域、儲存、金流）；`install.sh`（Zeabur／docker-compose）與 `deploy-cf.sh`（wrangler 一鍵：建 D1、R2、KV、Queue、secrets、migrate、deploy）；文件 | 客戶可自選平台一鍵部署 | 2 天 |

總計約 **11–16 個工作天**；M1 是關鍵路徑，做完 Zeabur 版本身也變乾淨（映像可瘦、可測）。

## 7. 平台選擇指南（給客戶）

| | Zeabur（容器） | Cloudflare（Workers） |
|---|---|---|
| 適合 | 需要 Postgres 完整功能、長任務、單機可控 | 流量尖峰大、想要零維運、預算低 |
| 月費概估 | 專用機 2C/4GB 起（現行） | Workers Paid 5 USD 起＋用量 |
| 資料庫 | PostgreSQL（不限大小） | D1（10 GB／庫；超過改 Hyperdrive＋外部 Postgres） |
| 檔案 | 伺服器硬碟或 R2 | R2（必要） |
| 長任務（AI 產圖、批量匯入） | 程序內佇列即可 | Queues（需 Paid 方案） |
| 冷啟動 | 無 | 極低（isolate） |
| 金流回呼 | 需公開 HTTPS（平台網域即可） | 同 |

## 8. 這次不做的事（明列以免誤解）

- 不做多租戶（一客戶一組部署，兩平台皆然）。
- 不把 NestJS 搬上 Cloudflare Containers（Containers 拿不到 D1 binding，違反「D1」前提）。
- 不用 Cloudflare Pages（已併入 Workers；OpenNext 官方路徑是 Workers）。
- Redis 在兩平台都移除。

## 9. 定位修正：給任何人「獨自部署」的套件（2026-09-23）

前提改變：不是一個站、也不是我們代客部署，而是**任何第三方在自己的帳號上一鍵部署**。這改變了三件事：

### 9.1 交付物必須是「按鈕」，不是「文件」

| 平台 | 一鍵機制 | 部署者需要準備 | 我們要維護的東西 |
|---|---|---|---|
| Zeabur | **Zeabur Template**（一份 template yaml：postgres＋api＋web，映像來自 GHCR 版本 tag，變數以表單詢問） | Zeabur 帳號、一個網域（或用平台子網域） | template yaml、GHCR 映像（CI 打 tag 自動推） |
| Cloudflare | **Workers＋D1 殼 `apps/worker`（v0.27.0，路線 B）**：nest-bridge 掛既有 187 條路由、D1 driver adapter、本機 14 檔 API e2e 全綠、CI `e2e-workers` | 正式 D1 已建（cfbc8c84…）；`wrangler deploy` 需帳號先註冊 workers.dev 子網域；前台 OpenNext 已做（v0.32.0：`apps/web` cf:build／cf:deploy，https://sitekit-web.sitekit-deploy-cloudflare.workers.dev 實測 SSR＋/api 代理正常；免費方案 api 冷啟動 5–8 秒）；Containers 路線 A 保留（需 Workers Paid） |

兩者共同前提：**所有設定都在後台「系統設定」而不是環境變數**；環境變數只剩 `DATABASE_URL`／bindings、`SESSION_SECRET`、`OPS_TOKEN`，而且後兩者要能**首次啟動自動產生**（顯示一次讓部署者抄下）。

### 9.2 原始碼可見性決定先做哪一邊

| 授權模式 | Zeabur（映像） | Cloudflare（按鈕） |
|---|---|---|
| 閉源／付費授權 | 可：部署者只拿到映像（可反編譯但門檻高） | 難：Deploy 按鈕要 clone 原始碼到部署者的 GitHub；替代是 `npx sitekit-deploy` 用 wrangler 推「已打包的 Worker bundle」，仍是可讀的 JS |
| 開源（MIT／AGPL） | 可 | 可，且最順 |

→ **閉源：Zeabur Template 先做；Cloudflare 走 CLI 安裝器。開源：兩個按鈕都做，Cloudflare 反而是更低成本的主推路徑。**

### 9.3 獨自部署帶來的新需求（原本單站不需要）

| 需求 | 做法 |
|---|---|
| 首次啟動精靈 | `/setup`：建立超級管理員→站名與網域→儲存（R2 必填於 CF、可選於 Zeabur）→Email（Resend）→金流（可略過）；完成前所有後台路由導到 `/setup` |
| 無示範資料 | seed 只建設定預設值；`admin@example.com`、示範課程、示範文章一律移除（本機開發用 `SEED_DEMO=1` 才建） |
| 自我診斷頁 | 系統設定→「健康檢查」：DB、儲存讀寫測試、寄一封測試信、金流回呼網址可達性、版本號；產出「支援包」（去識別化的設定與最近錯誤）給我們排障 |
| 版本更新 | api 定時查 `github.com/<org>/sitekit-releases/latest`（比照 FastCut）；後台顯示「有新版本」與該平台的更新步驟；Zeabur＝改 template 映像 tag 重部署（migrate 自動）、CF＝Workers Builds 追蹤 fork 的 main，部署者按 GitHub「Sync fork」 |
| 備份（✅ v0.24.0） | 內建：整庫 JSON 匯出／每日自動備份到伺服器備份目錄／後台一鍵還原／CLI export・import；跨 SQLite↔PostgreSQL 搬家。異地備份（R2）與 CF Cron 版待做 |
| 錯誤可觀測 | 錯誤連同 Next digest 寫進 `audit_logs`／`error_logs` 表，後台可看；不依賴平台日誌（部署者不會看） |
| 金鑰不落地 | 各家金流、AI、Resend 金鑰只存部署者自己的 DB（settings 表，機密欄遮蔽），我們永遠拿不到 |
| 授權與計費（若付費） | 啟動時向授權伺服器換 license token（離線寬限 7 天）；或純買斷不驗證。這是商業決策，架構上先留 `license` port |

### 9.3.1 Zeabur 手動部署實測（2026-09-24，單體殼）

repo 私有期間 Template 無法拉 GHCR 映像，改走「GitHub 來源＋儀表板貼 `Dockerfile.monolith`」：兩個服務（PostgreSQL＋sitekit）、埠 3000（刪預設 8080）、`/data` 磁碟、子網域綁 `:3000`，建置約 5 分鐘即上線並進 `/setup`。步驟與陷阱（`${POSTGRES_CONNECTION_STRING}` 會指向已刪除的舊 postgres）記在 README「Zeabur 實際部署」。Template 一鍵路線等 repo 公開後再驗證。

### 9.4 調整後的優先序

1. **M0＋M1**（測試護欄、抽 core）——不論哪個平台都是地基。
2. **首次啟動精靈＋自動產生機密＋去示範資料＋健康檢查頁**（✅ v0.19.0 完成）——沒有這四項，任何平台的「一鍵」都會卡在第一天。
3. **Zeabur Template＋GHCR 映像**（閉源可行、工作量最小：約 2 天）。
4. **M2＋M3**（D1 雙 schema、Hono 殼）→ **Deploy to Cloudflare 按鈕或 CLI 安裝器**。
5. 版本更新通知、備份服務、支援包。

## 10. 定位再修正：WordPress 式開放套件（2026-09-23）

「任何人獨自部署、每個客戶獨立系統、像 WordPress 一樣開放」→ 原始碼公開是前提，商業模式與 WordPress 同構：**核心免費開源，靠代管、付費擴充、教學課程、支援賺錢**（AIGC創客學堂本身就是「課程」這一環）。

### 10.1 WordPress 之所以是 WordPress 的五件事，對照 SiteKit 現況

| WordPress 要素 | SiteKit 現況 | 差距 |
|---|---|---|
| 一鍵安裝（5 分鐘安裝） | 需要 Zeabur 儀表板貼 Dockerfile＋手填環境變數 | Zeabur Template＋Deploy to Cloudflare 按鈕＋首次啟動精靈（第 9 節） |
| 外掛（hooks／filters） | 金流 5 家、物流 2 家、發票 3 家、AI 供應商 3 家都已是「adapter 介面＋註冊表」形狀；沒有事件匯流排、沒有第三方可掛的點 | 建 **事件匯流排**（`order.paid`、`user.registered`、`content.published`…）＋**擴充註冊表**（adapter／OPS 動作／後台頁／設計器區塊／指令台技能）；外掛＝npm 套件，**建置期載入**（`sitekit.config.ts` 列出），不做執行期動態載入（Workers 做不到、也是資安面） |
| 佈景主題 | `design.ts` 頁面設計文件、首頁區塊、品牌 token、20 組產圖模板 | 主題＝「設計 token＋頁面模板集＋區塊樣式」的 JSON 套件，可匯入匯出；已有 JSON 匯入基礎 |
| 更新機制（核心／外掛一鍵更新） | 無 | 統一 CLI（`npx sitekit update`）＋後台版本通知；外掛更新＝改 config 重建 |
| 生態（外掛市集、文件站、社群） | 無 | 文件站（VitePress／Next）、示範站、外掛市集晚於核心 v1.0 |

### 10.2 SiteKit 相對 WordPress 的差異化（不要做成 WordPress 複製品）

- **AI 原生**：後台雙路徑（MCP＋指令台）是 WordPress 沒有的；「外掛」的第三種形態＝**MCP 工具／指令台技能**，外部服務用 MCP 接進來即是外掛，不需要進程內載入。
- **台灣本地整合內建**：藍新／綠界／統一／LINE Pay／支付連、超商物流、電子發票三家——WordPress 要裝五個外掛才有的東西是核心功能。
- **型別安全＋單一真相源**：`OPS_ACTIONS` 同時是 MCP 工具、AI 指令台、後台 API 的定義，外掛註冊一個動作就三條路徑都有。

### 10.3 開放套件必須補的基礎（依序）

1. **授權**：repo 目前**沒有 LICENSE 檔**。選項：MIT（採用最廣、允許閉源分叉與 SaaS 化）、AGPL-3.0（防止雲端業者拿去做代管 SaaS 不回饋；但企業採用會猶豫）、GPL-2.0（與 WordPress 相同）。若商業模式包含「自家代管」，AGPL 最能保護；若要最大擴散，MIT。**核心 AGPL＋官方擴充商業授權**是常見折衷。
2. **去品牌化**：預設站名「AIGC創客架站套件」、品牌色、seed 內容要變成中性預設；品牌只留在「關於本套件」。
3. **i18n**（✅ v0.25.0 前台完成；後台待）：前台字串已抽成字典（zh-TW 預設、en 完整），後台維持繁中。
4. **資料可攜**（✅ v0.24.0 完整匯出／匯入）：已有 WordPress／CSV 匯入；補**完整匯出**（內容、商品、課程、訂單、設定、設計文件、上傳檔清單）＝「SiteKit 匯出檔」，也是備份格式與搬家格式。
5. **穩定的公開介面**：對外承諾語意化版本的三個面——REST（`/api/*`）、OPS 動作、設計文件 JSON schema；破壞性變更走 major。
6. **安全揭露流程**、CONTRIBUTING、CoC、Issue 模板、CI 對 PR 跑 e2e。
7. **遙測 opt-in**：只回報版本與平台，供你知道有多少活躍部署；預設關閉並在精靈告知。

## 11. 再擴大：一般商業網路主機也要能裝（2026-09-23）

WordPress 能到處裝，是因為它只需要「PHP＋MySQL」這個最低公分母。SiteKit 是 Node.js，最低公分母要重新定義：

### 11.1 主機類型與可行性

| 主機類型 | 例子 | 能裝嗎 | 需要的執行形態 |
|---|---|---|---|
| 純 PHP 虛擬主機（只有 PHP＋MySQL，無 Node） | 大多數台灣入門型虛擬主機 | **不能**（除非用 PHP 重寫，不做） | — |
| 有 Node 的虛擬主機（cPanel「Setup Node.js App」／Passenger、Plesk Node） | 中高階虛擬主機、部分台灣主機商 | 能 | **單體模式**：一個 Node 程序聽一個 PORT，資料庫用主機給的 MySQL 或 SQLite 檔 |
| VPS／雲主機（有 root） | Hetzner、Linode、GCP、HiCloud、遠傳、任何 Docker 主機 | 能 | 單體模式（`npx sitekit start`）或 docker-compose |
| PaaS 容器平台 | Zeabur、Railway、Fly、Render | 能 | 容器（單體或 web＋api 分離） |
| 無伺服器 | Cloudflare Workers＋D1 | 能 | Workers 殼 |
| 本機試用 | Windows／mac 一台電腦 | 能 | 單體模式＋SQLite，`npx sitekit start` 即開 |

→ 真正的 WordPress 對應物是**「單一 Node 程序＋SQLite 檔＋伺服器硬碟上傳」的單體模式**：Node 20 就能跑，沒有 Postgres、沒有 Redis、沒有反向代理。這是預設安裝形態；Postgres／MySQL、R2、分離部署都是「升級選項」。

### 11.2 架構調整：三個殼、三種資料庫

```
packages/core     業務邏輯（不變）
packages/db       一份模型 → 產生 postgres / mysql / sqlite 三份 Prisma schema 與 migration
                  （sqlite 版同時服務「本機 SQLite 檔」與「Cloudflare D1」）
apps/
  server/   ★單體殼（預設；✅ v0.21.0 完成）：Next.js custom server 同程序掛 API（route handlers 直接呼叫 core，
            不經 HTTP 反向代理）；PORT 由環境給；SQLite 或 DATABASE_URL；上傳存本機；cron 由
            主機 crontab 打 /api/cron 或程序內 setInterval；佇列程序內
  api/      分離殼（可選）：NestJS，給想要 web／api 分開擴展的容器部署（Zeabur 現行）
  worker/   Workers 殼：Hono＋D1
```

- **`apps/server` 可以取代 Zeabur 的兩個容器**：Zeabur Template 改成單一 `server` 服務＋postgres，更簡單。分離殼保留給真的需要獨立擴展 API 的客戶。
- **Mailer port 要加 SMTP**（nodemailer）：商業主機客戶通常有自己的 SMTP，不會都去申請 Resend。Resend／SMTP／log 三選一，後台設定。
- **Storage port**：伺服器硬碟為預設；S3／R2 為選項；Workers 只有 R2。
- **Db port 的交易規則以最弱的 D1 為準**（batch 式、條件式更新），這樣三種資料庫共用一套 core 邏輯。
- **MySQL 差異**：Json、enum 都支援；`String[]` 同 sqlite 用 JSON 字串；`citext`／`ILIKE` 之類 Postgres 特有語法禁止進 core（目前會員搜尋用 Prisma `mode: 'insensitive'`，Prisma 會在 MySQL 自動處理，SQLite 不支援 → 改成 lower() 比對）。

### 11.3 安裝體驗目標（對齊 WordPress 的「5 分鐘安裝」）

| 情境 | 步驟 |
|---|---|
| VPS／本機 | `npx sitekit@latest init my-site` → 問埠號與資料庫（預設 SQLite）→ `npx sitekit start` → 瀏覽器開 `/setup` 精靈 |
| cPanel Node 主機 | 上傳 release 壓縮包（已含 `node_modules` 與建置產物，避免主機上跑 `npm install`）→ 在「Setup Node.js App」指定 `server.js` 與 PORT → 開 `/setup` |
| Docker 主機 | `docker run -v ./data:/data -p 3000:3000 ghcr.io/<org>/sitekit`（單一映像、SQLite 預設） |
| Zeabur | Template 一鍵 |
| Cloudflare | **Workers＋D1 殼 `apps/worker`（v0.27.0，路線 B）**：nest-bridge 掛既有 187 條路由、D1 driver adapter、本機 14 檔 API e2e 全綠、CI `e2e-workers` | 正式 D1 已建（cfbc8c84…）；`wrangler deploy` 需帳號先註冊 workers.dev 子網域；前台 OpenNext 已做（v0.32.0：`apps/web` cf:build／cf:deploy，https://sitekit-web.sitekit-deploy-cloudflare.workers.dev 實測 SSR＋/api 代理正常；免費方案 api 冷啟動 5–8 秒）；Containers 路線 A 保留（需 Workers Paid） |
| 更新 | `npx sitekit update`（下載新版、跑遷移、重啟）；cPanel 客戶＝上傳新壓縮包後點 Restart；容器＝換 tag |

### 11.4 對優先序的影響

單體殼 `apps/server` 提前到 **1.0**，因為它同時是：本機試用、VPS、cPanel Node 主機、Docker 單映像、Zeabur 簡化版的共同基礎。分離殼（現行 NestJS）降為可選；Workers 殼維持 1.2。
SQLite 支援因此從「為了 D1 才做」變成「預設資料庫」，M2 的價值提高、風險攤平（先在本機 SQLite 驗證，再上 D1）。

**不做的事**：PHP 版；執行期動態載入外掛；把 Postgres 特有功能當核心依賴。

## 13. 部署平台定案：Zeabur 預設、Cloudflare 次要（2026-09-25）

依第 12 節實測與 CP 值評估（月費／持久性／功能完整度／台灣延遲／維運），使用者定案：

| 層級 | 平台 | 定位 | 交付物 |
|---|---|---|---|
| **預設推薦** | Zeabur（專用伺服器或 Serverless） | 功能 100%、硬碟持久、東京節點對台灣延遲最好、儀表板零維運；一個客戶一套 | Zeabur Template 一鍵（`deploy/zeabur-template.yaml`，GHCR 映像已公開）＋README 手動步驟 |
| **次要** | Cloudflare Workers＋D1＋R2 | 零維運、全球邊緣；免費方案 CPU 10ms 不夠跑密碼雜湊→實際建議付費方案 US$5；前台待 OpenNext | `apps/worker`＋`deploy/cloudflare` |
| 可用 | VPS＋docker-compose、Render、Railway、Fly、cPanel Node | 客戶已有主機或有特殊需求時 | 設定檔與 README 一頁步驟 |
| 不做 | Firebase（需 Blaze＋Cloud Run）、Vercel／Netlify 靜態、純 PHP 主機 | — | — |

對後續工作的影響（優先序）：
1. **Zeabur Template 實際匯入驗證**（映像公開後可行）：一鍵建 PostgreSQL＋sitekit、掛 /data、綁網域、進 /setup；README「最快開站」第一段改成 Zeabur 按鈕。
